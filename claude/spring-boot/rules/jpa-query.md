# JPA 조회

`<<결정>>`은 프로젝트가 채운다. Result 생성 방식은 설치된 `result-creation.md`를 따른다.

## 설정
- `spring.jpa.open-in-view=false`.
- 지연 로딩 컬렉션의 배치 크기(`default_batch_fetch_size`): `<<결정>>`.

## N+1
- 루프 안에서 Repository를 호출하지 않는다.
- 연관 데이터가 필요한 조회는 아래 중 하나를 택한다: fetch join / `@EntityGraph` / 배치 페치 / 전용 조회 쿼리(Result 프로젝션). 선택 기준과 이유를 주석이나 PR에 남긴다.
- 컬렉션을 fetch join하면서 페이징하면 메모리에서 페이징되어 위험하다. 이 경우 ToOne만 fetch join하고 컬렉션은 배치 페치를 쓴다.
- 둘 이상의 컬렉션을 한 쿼리에서 fetch join하지 않는다.

## 페이징·정렬
- 목록 조회는 페이징을 기본으로 한다. 최대 page size를 제한한다(`<<결정>>`).
- 정렬 기준에 유일한 키(예: id)를 포함해 결과 순서를 안정적으로 만든다.
- 총 개수 쿼리가 비싸면 카운트 생략/커서 방식을 `<<결정>>`한다.

## 쿼리 작성
- 단순 조회는 Spring Data 메서드 이름 쿼리 또는 `@Query`. 동적 조건·프로젝션이 필요하면 `<<결정: QueryDSL/Criteria/JdbcClient 등>>`.
- 쿼리 메서드 이름이 과도하게 길어지면 `@Query`나 별도 구현으로 옮긴다.
- 네이티브 쿼리는 JPQL로 안 되는 경우에만 쓰고 이유를 남긴다.
- 벌크 수정(`@Modifying`)은 영속성 컨텍스트와 불일치가 생기므로 실행 후 컨텍스트 초기화 여부를 확인한다.
- 조회에서 필요한 컬럼만 가져올 수 있으면 엔티티 전체 대신 프로젝션을 쓴다.
- 자주 쓰는 조건에는 인덱스를 확인한다(실행 계획 확인: `<<결정>>`).

## 검증
- 목록 조회 테스트에서 발생 쿼리 수를 확인한다(`<<결정: 도구>>`). N+1이 기대 수보다 많으면 실패로 본다.
