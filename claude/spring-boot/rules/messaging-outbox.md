# 메시징과 Outbox

메시지(이벤트)로 다른 모듈·서비스에 알려야 할 때의 규칙이다. 브로커(Kafka, Redis Streams, RabbitMQ 등)는 `<<결정>>`. 같은 JVM 안의 단순 알림은 `transaction.md`의 `@TransactionalEventListener`로 충분한지 먼저 본다.

## 발행: Outbox
- DB 상태 변경과 메시지 발행이 둘 다 보장되어야 하면 Outbox를 쓴다. 상태 변경과 같은 트랜잭션에서 outbox 테이블에 이벤트 행을 저장한다.
- 별도 릴레이가 outbox 행을 읽어 브로커에 발행한다(폴링 또는 CDC: `<<결정>>`). 발행 성공 후 상태(`published` 등)를 갱신한다.
- 트랜잭션 안에서 브로커에 직접 발행하지 않는다. 커밋 이후 발행(`AFTER_COMMIT`)만으로는 발행 실패 시 메시지가 유실될 수 있다.
- outbox 행에는 이벤트 id(고유), 종류, 집계 식별자, 페이로드, 상태, 생성 시각을 둔다. 순서가 중요하면 순서 키: `<<결정>>`.
- 릴레이가 다중 인스턴스로 돌 때 중복 발행/경합을 막는 방법: `<<결정>>`(`concurrency.md` 참조).
- 브로커 장애가 애플리케이션 전체로 번지지 않도록 릴레이에 장애 대응(서킷브레이커, 백오프)을 둔다.
- 발행된 outbox 행의 정리(보관/삭제) 정책: `<<결정>>`.

## 소비: 멱등성
- 발행은 최소 한 번(at-least-once) 전달이다. 같은 메시지가 두 번 올 수 있으므로 소비자는 멱등해야 한다.
- 이벤트 id로 처리 이력을 저장해 중복을 걸러내거나, 처리 자체를 멱등하게 설계한다(유니크 제약 등).
- 처리에 실패한 메시지를 ACK(확인)하지 않는다. 예외를 삼키고 ACK하면 메시지가 유실된다.
- 재시도는 제한 횟수 + 백오프로 하고, 한계를 넘으면 DLQ/DLT(dead letter)로 보낸다. 무한 재시도로 다음 메시지를 막지 않는다. 독성 메시지(계속 실패하는 메시지)를 격리한다.
- 소비자 처리 중 외부 호출과 DB 트랜잭션 경계는 `transaction.md`를 따른다.

## 계약
- 메시지 스키마(필드, 이름, 버전)는 한 곳에서 정의한다. 발행자와 소비자가 각자 중복 정의해 어긋나지 않게 한다(위치: `<<결정>>`; MSA에서는 `msa-overlay` 참조).
- 필드 추가는 하위 호환으로 하고, 소비자는 모르는 필드를 무시한다.
- 메시지에 엔티티를 직렬화하지 않는다. 별도 이벤트 페이로드 타입을 쓴다.

## 브로커별 확인 사항 (해당하는 것만)
- Kafka: 소비자 오류 처리(재시도, DLT)를 `DefaultErrorHandler`와 BackOff로 설정한다. 일부 `Error` 계열 예외는 핸들러를 우회할 수 있다.
- Redis Streams: 소비자 그룹의 pending 목록을 관리한다. 처리 완료 후 `XACK`, 오래 방치된 pending은 `XAUTOCLAIM`/`XCLAIM`으로 회수한다.

## 근거
- [자료] microservices.io(Transactional outbox, Idempotent consumer), 우아한형제들(AFTER_COMMIT 발행의 한계와 Outbox), Spring Kafka·Redis Streams 문서. 읽은 문서 일부는 최신 버전 기준이므로 대상 버전에서 확인한다.
