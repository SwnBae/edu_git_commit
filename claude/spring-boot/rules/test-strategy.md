# 테스트 전략

작성 형식은 `test-given-when-then.md`를 따른다. `<<결정>>`은 프로젝트가 채운다.

## 종류와 선택
| 종류 | 대상 | 방법 |
|---|---|---|
| 단위 | 도메인 객체, Service 로직, 변환 메서드 | Spring 컨텍스트 없이 JUnit + Mockito. 가장 많이 작성 |
| 웹 슬라이스 | Controller 매핑, 검증, 예외 응답 | `@WebMvcTest` + Service 목 |
| 영속 슬라이스 | Repository, 쿼리, 매핑 | `@DataJpaTest` |
| 통합 | 주요 흐름 일부 | `@SpringBootTest` — 개수를 제한한다 |
| 구조 | 계층·의존 규칙 | ArchUnit 테스트 |

- Boot 4의 테스트 어노테이션 패키지·스타터 이름은 3.x와 다를 수 있다. 프로젝트의 빌드 파일 의존성과 대상 버전 문서로 확인한다.
- DB 의존 테스트의 데이터베이스는 `<<결정: 운영과 같은 종류를 컨테이너로 / 인메모리>>`. 운영 DB와 다른 DB를 쓰면 방언 차이를 놓칠 수 있다.

## 규칙
- 버그를 고칠 때는 그 버그를 재현하는 테스트를 먼저 추가한다.
- 외부 시스템(HTTP, 메시징)은 테스트에서 실제로 호출하지 않는다. 테스트용 대역(Mock server, 스텁)을 쓴다.
- 우리가 소유하지 않은 타입(서드파티 클라이언트)을 직접 목킹하지 말고, 감싼 인터페이스(`external-client.md`의 클라이언트)를 목킹한다.
- 시간·난수·UUID는 주입해서 고정한다.
- 테스트는 서로 독립이다. 순서·공유 상태에 의존하지 않는다. DB 상태는 테스트마다 정리한다.
- 검증은 결과(상태, 반환값, 예외)를 우선한다. 호출 횟수 검증은 그것이 요구사항일 때만 한다.
- 커버리지 목표: `<<결정>>`. 수치를 채우려고 의미 없는 테스트를 쓰지 않는다.
- 실패 메시지만으로 원인을 알 수 있게 AssertJ 단언을 구체적으로 쓴다.

## ArchUnit
- 선택한 `package-structure`와 `service-layering`의 검증 항목을 테스트로 옮긴다. 기존 위반은 `FreezingArchRule.freeze`로 고정하고 신규 위반만 막는다.
