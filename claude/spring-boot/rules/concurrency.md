# 동시성

수치와 선택은 `<<결정>>`. 락은 마지막 수단이고, 먼저 충돌이 안 나는 설계를 본다.

## 기본 원칙
- 싱글톤 빈(Service, Component)은 상태를 갖지 않는다. 변경 가능한 필드를 두지 않는다.
- 데이터 정합성의 마지막 방어선은 DB 제약(유니크, 외래 키, 체크)이다. 애플리케이션 락만 믿지 않는다.
- 재시도될 수 있는 쓰기는 멱등하게 설계한다(멱등키, 유니크 제약).

## 락 선택
| 상황 | 선택 |
|---|---|
| 충돌이 드문 일반 수정 | 낙관적 락 — 엔티티에 `@Version` |
| 충돌이 잦고 정확히 한 번 처리해야 하는 갱신 | 비관적 락(`PESSIMISTIC_WRITE` 등), 또는 원자적 UPDATE 쿼리 |
| 여러 인스턴스에 걸친 임계 구역이 DB 락으로 못 풀릴 때 | 분산 락(Redis/Redisson 등) — 마지막 수단 |
| 여러 인스턴스에서 스케줄 작업이 한 번만 실행되어야 할 때 | 스케줄 락(ShedLock 등) |

- 낙관적 락 충돌(`OptimisticLockException` 계열)은 재시도 횟수를 제한해 처리하거나 사용자에게 충돌을 알린다. 무한 재시도하지 않는다.
- 비관적 락은 잠금 순서를 일관되게 해 교착을 피하고, 락 대기 시간 제한을 둔다.

## 분산 락 사용 시
- 락 획득 결과를 반드시 확인한다(`tryLock`의 반환값). 획득하지 못했으면 진행하지 않는다.
- 락에는 TTL(만료)을 둔다. 작업이 TTL보다 길어질 수 있으면 갱신 방식이나 작업 분할을 설계한다.
- 해제는 `finally`에서 하고, 락을 건 스레드/소유자만 해제한다.
- **락의 범위는 트랜잭션보다 넓게** 잡는다. 순서는 `락 획득 → 트랜잭션 시작 → 커밋 → 락 해제`다. 트랜잭션 안에서 락을 해제하면 커밋 전에 다른 요청이 들어와 변경 전 값을 읽는다. 락 처리와 트랜잭션 메서드는 서로 다른 빈으로 분리한다(`transaction.md`의 self-invocation 주의).
- 복제 지연·장애 조치 상황에서 Redis 락은 상호 배제를 완전히 보장하지 않을 수 있다. 정합성이 중요하면 DB 제약이나 펜싱 토큰으로 보강한다.

## 스케줄 락 사용 시
- `lockAtMostFor`(비정상 종료 대비 상한)와 `lockAtLeastFor`를 작업 특성에 맞게 정한다: `<<결정>>`.
- 인스턴스 간 시계 차이가 있을 수 있음을 고려한다. 스케줄 락은 스케줄러가 아니라 중복 실행 방지 장치다.

## 비동기 처리
- `@Async`/스레드 풀은 크기와 큐를 제한한 전용 Executor를 쓴다: `<<결정>>`. 무제한 스레드/큐를 쓰지 않는다.
- 트랜잭션과 보안 컨텍스트는 다른 스레드로 전파되지 않는다. 새 스레드에서 필요한 트랜잭션은 그쪽에서 시작한다.
- 비동기 작업의 실패는 반드시 로깅 또는 재처리 경로를 둔다.

## 근거
