# 선택형 규칙 (options)

서로 모순되는 규칙을 같이 설치하면 Claude가 임의로 하나를 따를 수 있다. 그래서 그룹마다 **하나만** 골라 `.claude/rules/`에 설치한다(`install.sh` 참조). 설치되면 파일 이름은 그룹 이름이 된다(`package-structure.md` 등).

## 1. package-structure — 폴더 구조
| 선택지 | 맞는 상황 | 장점 | 단점 |
|---|---|---|---|
| `layered` | 작은 규모, 도메인 몇 개 | 단순하고 익숙하다. 시작이 빠르다. | 도메인이 늘면 한 폴더에 클래스가 쌓이고 도메인 경계가 흐려진다. 나중에 분리하기 어렵다. |
| `domain-first` | 큰 규모, 도메인 여러 개, 팀 분할 | 도메인 단위로 코드가 모인다. 경계가 명확하고 분리·모듈화에 유리하다. | 도메인 간 의존을 의식적으로 관리해야 한다. 공통 코드 위치 판단이 필요하다. |
| `hexagonal` | 큰 규모 + 복잡한 도메인 로직, 기술 교체/도메인 단독 테스트 중요 | 도메인이 프레임워크와 분리된다. 어댑터 교체와 테스트가 쉽다. | 매핑 코드와 파일 수가 늘어난다. 단순 CRUD에는 과하다. |
| `msa-overlay` (위 중 하나에 추가) | 서비스가 여러 개이거나 분리 예정 | 서비스 경계 규칙(DB 분리, 계약, id 참조, 보상 트랜잭션)을 명시한다. | 계약 공유 방식과 분리 절차는 아직 미조사. 운영 복잡도가 크게 늘어난다. |

## 2. service-layering — 서비스 단계 규칙
요구사항 "위에서 아래로 내려가는 구조, 윗단계에서 아래 정보를 가져올 수 없다"는 두 가지로 해석할 수 있어 둘 다 둔다.
| 선택지 | 의미 | 장점 | 단점 |
|---|---|---|---|
| `one-way-dependency` | 호출 방향만 단방향. 아래는 위를 주입·import하지 않는다. | 규칙이 단순하다. ArchUnit으로 쉽게 강제한다. 순환 의존이 막힌다. | 아래 단계의 타입(엔티티 등)이 위로 올라오는 것은 막지 못한다. |
| `type-isolation` | 위 규칙 + 아래 단계의 내부 타입(엔티티·리포지토리)이 위로 올라오지 않는다. | 단계 사이 결합이 가장 낮다. 지연 로딩 프록시 누수를 막는다. | Result 등 변환 타입이 늘고 서비스 메서드가 많아진다. 검증 규칙을 직접 짜야 한다. |

## 3. result-creation — Result 만드는 위치
| 선택지 | 의미 | 장점 | 단점 |
|---|---|---|---|
| `query-repository` | 조회 Repository가 Result를 직접 반환 | 필요한 컬럼만 조회해 효율적이다. 엔티티 로딩·N+1 부담이 적다. | Repository가 DTO를 알게 된다. 쿼리 작성(JPQL/QueryDSL)이 필요하다. |
| `service-converts` | Repository는 엔티티 반환, Service가 변환 | Repository가 단순하다(Spring Data 기본 사용). 엔티티 규칙이 한곳에 모인다. | 엔티티 전체를 로딩한다. 변환 중 지연 로딩·N+1 위험이 있다. |

## 선택하는 기준 요약
- 작게 시작: `layered` + `one-way-dependency` + `service-converts`
- 크게: `domain-first`(또는 `hexagonal`) + `type-isolation` + `query-repository`(조회가 무거울 때)
- 위는 예시 조합이다. 그룹은 서로 독립이므로 어떻게 조합해도 된다.
