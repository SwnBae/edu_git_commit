# 서비스 단계 — 단방향 의존형

서비스 계층을 단계로 나누고, **의존(호출)이 위에서 아래로만** 흐르게 한다. 아래 단계는 위 단계를 알지 못한다(주입·import하지 않는다). 단계 사이에서 값을 주고받는 타입은 제한하지 않는다.

## 단계 (이름은 `<<결정>>`)
| 단계 | 예시 이름 | 책임 | 트랜잭션 |
|---|---|---|---|
| 1 (위) | `{Domain}Facade` / 유스케이스 서비스 | 여러 작업의 순서 조립, 외부 시스템 호출, 응답 변환 | 걸지 않는다 |
| 2 (아래) | `{Domain}Service` + `{Domain}ServiceImpl` | DB 읽기/쓰기 단위 업무, 도메인 규칙 | Impl에 `@Transactional` |
| 3 | Repository | 영속화 | 2단계의 트랜잭션에 참여 |

## 규칙
- 호출은 1 → 2 → 3 방향만 허용한다. 2단계가 1단계를 주입받으면 위반이다.
- 같은 단계의 서비스끼리 서로 호출하지 않는다. 공통 로직이 필요하면 아래 단계로 내리거나 별도 컴포넌트로 뽑는다.
- 외부 시스템 호출(`client`)은 1단계에서만 한다. 트랜잭션이 걸린 2단계 메서드 안에서 하지 않는다.
- 1단계에서 하나의 업무 흐름이 여러 2단계 메서드를 호출하면, 각 호출이 별도 트랜잭션이다. 전체를 원자적으로 묶어야 하면 2단계에 그 단위의 메서드를 새로 만든다.
- 같은 클래스 안에서 `@Transactional` 메서드를 `this`로 호출하지 않는다(프록시가 적용되지 않는다). 트랜잭션 단위가 달라지면 클래스를 나눈다.
- 서비스는 인터페이스 + Impl 쌍으로 만들고 `@Transactional`은 Impl에 붙인다. 1단계(Facade)는 인터페이스 없이 구체 클래스로 두어도 되는지: `<<결정>>`

## 검증 (ArchUnit 제안)
- 2단계 패키지의 클래스가 1단계 패키지를 참조하지 않는지.
- `client` 패키지를 참조하는 클래스가 1단계뿐인지.
