# 패키지 구조 — MSA 보강 (overlay)

`layered`, `domain-first`, `hexagonal` 중 하나에 **추가로** 설치한다. 서비스가 둘 이상으로 나뉘거나 나뉠 예정일 때 쓴다.
근거: [자료] 서비스마다 자기 DB를 갖는다(database per service). 모노리스로 시작해 경계가 드러나면 나누는 접근이 흔하다(Monolith First).

## 규칙
- 서비스 하나는 자기 데이터베이스(스키마)만 접근한다. 다른 서비스의 테이블을 직접 읽지 않는다.
- 다른 서비스의 엔티티, 리포지토리를 코드 수준으로 공유하지 않는다. 서비스 사이에는 API와 이벤트 계약으로만 소통한다.
- 다른 서비스는 "외부 시스템"으로 취급한다. 동기 호출은 `external-client` 규칙(전용 클라이언트, 타임아웃, 예외 변환)을 따른다.
- 서비스 경계를 넘는 참조는 id로만 한다. 엔티티 연관관계(`@ManyToOne` 등)를 서비스 경계 너머로 만들지 않는다.
- 서비스 경계를 넘는 상태 변경은 단일 DB 트랜잭션으로 묶지 못한다. 보상(Saga)이나 이벤트 기반 최종 일관성으로 설계한다: `<<결정>>`. 이벤트 발행은 `messaging-outbox` 규칙을 따른다.
- 서비스 간 계약(API 스키마, 이벤트 스키마)에는 버전을 둔다. 필드 추가는 하위 호환으로 한다.
- 계약을 어디에 두고 공유할지(공유 계약 모듈 / 스키마 저장소 / 서비스별 복사): `<<결정>>`
- 읽기 조합이 필요한 화면은 API 조합이나 읽기 전용 모델로 푼다: `<<결정>>`

## 미조사 항목
- 계약 공유 방식의 비교, 모노리스에서 서비스를 떼어내는 구체 절차는 아직 조사하지 않았다. 확정 전에 조사한다.
